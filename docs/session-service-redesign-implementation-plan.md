### G0.1: approved startup membership and rollback contract

Task immediately inserts the provisional session and makes it active. Controller persists the STARTING reservation before execution begins. `newSession()` awaits readiness and returns that same session without duplicate insertion. No separate pending-operation storage representation is required. <!-- consolidation: exists; ref: docs/architecture/task.md#session-relationship-operations; reason: newSession and reserveSession preserve immediate single insertion and awaited completion. --> <!-- consolidation: discard; ref: docs/BLUEPRINT.md#decision-reconciliation; reason: STARTING and exact recovery representation are not frozen target schema. -->

Any critical creation failure, including final persistence failure after the process starts, triggers controller-coordinated rollback: stop/release the newly created execution, remove the provisional session through `Task.rollbackSession(creation)`, conditionally restore the previous selection, persist rollback, and report the original error. If another session is now selected, preserve that selection. Successful rollback removes the failed creation rather than retaining a failed history entry. <!-- consolidation: exists; ref: docs/specs/sessions.md#creation-failure-and-recovery; reason: Critical failure cleanup conditional removal and durable rollback are explicit. -->

Errors originate in the failing layer and bubble to the controller. Session does not interpret Harness startup errors or add catch-and-rethrow boilerplate. Harness cleans up resources allocated before it can return an execution handle; Session owns cleanup of its execution. Cleanup catches preserve the original failure and expose secondary failures. <!-- consolidation: exists; ref: docs/architecture/session-harness.md#readiness-evidence-and-failure-stages; reason: Harness errors bubble to application. --> <!-- consolidation: exists; ref: docs/architecture/session-harness.md#harness-construction-and-promises; reason: Partial allocations require cleanup and retained evidence. --> <!-- consolidation: exists; ref: docs/CONVENTIONS.md#error-handling-and-cleanup; reason: Cleanup preserves primary and secondary failures. -->

If rollback fails, report both failures and retain startup/ownership evidence for recovery. Do not remove the last tracking information for an execution that could not be stopped or claim that an unsuccessful durable rollback completed. This approved policy supersedes the old recommendation to preserve a confirmed-live execution on critical creation failure. Predecessor-retirement failure after successful successor creation remains a separate hand-off outcome and retains the successor. <!-- consolidation: exists; ref: docs/specs/sessions.md#creation-failure-and-recovery; reason: Incomplete rollback retains evidence and truthful error reporting. --> <!-- consolidation: exists; ref: docs/specs/sessions.md#handoff; reason: Retirement failure retains successful successor separately. -->
