## Decision 1 — What to do about duplicate-task repair

**Situation.** `src/core/duplicate-task-repair.ts:430-438` refuses to repair a duplicate held in *canonical task containers*: "canonical task-container duplicates require whole-container repair and are currently refused to preserve sibling artifacts and sidecars." <!-- consolidation: discard; ref: none; reason: Retired repair implementation evidence. --> Consequences: 7 assertions expect repair to work (6 in `src/test/cli-doctor.test.ts`, 1 in `src/test/container-duplicate-repair-contract.test.ts:97`), and `src/test/duplicate-task-repair.test.ts` has 20 failures because its fixtures *are* legacy flat duplicate scenarios. <!-- consolidation: discard; ref: none; reason: Historical failing-fixture counts. -->

**Why it matters.** It decides whether the product self-heals corrupted data or reports it — and it is the largest single block keeping the suite red. <!-- consolidation: discard; ref: none; reason: Historical decision motivation superseded by settled report-and-refuse ruling. -->

**Related wart found during the fixture work.** `src/core/duplicate-task-repair.ts:139-143` still derives a record's "logical path" from the basename and a `" - "` separator — a flat-filename assumption. Every canonical record's basename is `task.md`, so that helper is degenerate; it is only prevented from collapsing records together because grouping happens by canonical id first (`:165-172`). <!-- consolidation: discard; ref: none; reason: Retired repair-source defect evidence. --> Whichever option you choose, this helper should be deleted or re-derived from the canonical path rather than left as a trap. <!-- consolidation: discard; ref: none; reason: Obsolete repair helper recommendation superseded by feature removal. -->

**Context that changed the picture.** The collision's source is now closed: allocation reserves logical identities across active, completed, archived, and draft stores (`src/core/backlog.ts:557-571`), so normal use can no longer mint a duplicate. Remaining duplicates are hand-made or already-damaged data. <!-- consolidation: discard; ref: none; reason: Historical allocator conformance claim not current verification. -->

**Options.**
- **(a) Implement whole-container repair.** Destructive: pick a winner, merge the loser, preserve its artifacts and sidecars. Medium work, real data-loss risk, and it needs a design pass first. <!-- consolidation: discard; ref: docs/CONVENTIONS.md#changes-and-refactoring; reason: Rejected repair alternative after settled report-and-refuse decision. -->
- **(b) Keep the refusal; rewrite the expectations** to assert a blocked preview and no mutation, and restrict the legacy suite to canonical cases. Small. <!-- consolidation: discard; ref: none; reason: Unchosen alternative superseded by repair feature deletion. -->
- **(c) Delete the repair feature**, keeping duplicate reporting only. Smallest surface; loses detection value. <!-- consolidation: discard; ref: none; reason: Historical option text duplicates the settled ruling mapped above. -->

**Recommendation: (b).** The only remaining duplicates are damaged or hand-made — exactly when a human should look before anything merges. It matches the manual-repair stance already adopted. Choose (a) only if you want the product to self-heal; then I'd want the artifact-preservation design agreed before code is written. <!-- consolidation: discard; ref: none; reason: Old recommendation superseded by settled repair removal. -->

## Decision 2 — How far to take the session-identity refactor

**Situation.** An adapter exposes `nativeSessionIdForLaunch()`; shared orchestration calls it during *reservation* and writes the value into the durable record **before launch** (`src/agent-workspace/sessions.ts:941-966,1537-1553,1636-1655`), then picks `prepared.nativeSessionId ?? options.nativeSessionId` (`session-launch.ts:215-218`). One adapter sets `waitsForNativeSessionReceipt` (OpenCode v1). <!-- consolidation: discard; ref: none; reason: Historical identity-leak implementation evidence. -->

**The verdict.** Oracle judged this a genuine agent-agnosticism violation — not because harnesses differ, but because *shared code interprets provider mechanics and decides which adapter's id to trust.* <!-- consolidation: exists; ref: docs/architecture/session-harness.md#harness; reason: Provider identity and receipt mechanics belong inside Harness. --> Two supporting facts:

- The flag **does not implement a wait**: `bindNativeReceipt` samples and returns immediately if absent (`sessions.ts:389-400`), so the same harness gets different timing by entrypoint (workspace launch stays `STARTING`, direct launch goes `RUNNING`). <!-- consolidation: discard; ref: none; reason: Historical receipt timing defect evidence. -->
- Three sibling leaks of the same shape: `SessionStore` parsing OpenCode `ses_` identity (`session-store.ts:37,839-863`, and it gates on the literal preset name at `:860`); <!-- consolidation: discard; ref: none; reason: Historical storage provider leak. --> provider-name id generation in orchestration (`sessions.ts:1169-1187`); <!-- consolidation: discard; ref: none; reason: Historical orchestration provider leak. --> `mode-model.ts` owning OpenCode export schemas while rejecting non-OpenCode sessions. <!-- consolidation: discard; ref: docs/specs/interfaces.md#supported-integration-operations; reason: Provider restriction is superseded by provider-independent model capture. -->

**A correction you should have.** An earlier suspicion — that OpenCode v2 stores a *fictional* identity — is **refuted**. The installed `opencode` is v1.19.0; v2 is the separate `opencode2` binary (v2.0.26), whose `--session` is documented as "continue, or create if it does not exist." Verified locally: a fabricated `ses_<32 hex>` id creates a session under exactly that id, and re-running resumes it. So for v2 the client-chosen id *is* the provider identity, and the repo stores it correctly. <!-- consolidation: discard; ref: none; reason: Bounded OpenCode version and identity experiment evidence. --> Claude documents `--session-id` as establishing the conversation and can confirm identity later via `SessionStart.session_id`. <!-- consolidation: discard; ref: none; reason: Provider-specific external evidence belongs with adapter verification. --> Pi documents `--session-id` as create-if-absent but its `session_start` event carries **no id**, so it cannot confirm at all. <!-- consolidation: discard; ref: none; reason: Provider-specific event evidence is not a universal contract. --> A strict "provider-confirmed identity" rule is therefore unachievable for Pi and wrong for v2 — the contract must treat **client-established identity as a first-class case**. <!-- consolidation: integrate; ref: docs/architecture/session-harness.md#harness; reason: Settled adapter identity decision needs explicit client-established versus later-confirmed identity distinction. -->

**Options.**
- **(i) Bounded first slice (oracle's recommendation).** Adapters take `{kind:"new"} | {kind:"resume", nativeSessionId}` and return confirmed-or-client-established identity; adapters own proposed ids and final command assembly; <!-- consolidation: exists; ref: docs/architecture/session-harness.md#harness; reason: Harness owns new versus exact resume and established identity. --> one ownership-checked publisher handles immediate and deferred identity; OpenCode receipts route through it and storage stops hydrating identity; <!-- consolidation: exists; ref: docs/BLUEPRINT.md#application-controller-and-stores; reason: Validated application publication owns durability rather than storage provider interpretation. --> delete the flag **and** the requested-id plumbing together. <!-- consolidation: discard; ref: none; reason: Historical refactor step. --> Receipts stay durable. <!-- consolidation: unconfirmed; ref: docs/BLUEPRINT.md#durable-conversation-and-operation-records; reason: Exact receipt persistence need requires current recovery evidence. --> Medium cross-cutting refactor; no schema migration; lands in the region fix-58 just changed. <!-- consolidation: discard; ref: none; reason: Historical effort and patch-location estimate. -->
- **(ii) Full end state.** Also delete durable receipt transport — not honest yet; nothing verified replaces its recovery function. <!-- consolidation: unconfirmed; ref: docs/BLUEPRINT.md#durable-conversation-and-operation-records; reason: Preserve recovery-evidence removal gate until replacement is verified. -->
- **(iii) Narrow.** Fix only the live hazard and leave the interface alone. Given the v2 correction, no wrong data is being stored today, so this is now optional tidiness rather than a bug fix. <!-- consolidation: discard; ref: docs/BLUEPRINT.md#component-ownership; reason: Unchosen narrow alternative superseded by provider-owned identity. -->
- **(iv) Defer.** Capture as a spec and keep the current guard. <!-- consolidation: discard; ref: none; reason: Unchosen deferral superseded by settled first slice. -->

**Recommendation: (i), at low urgency.** Nothing is broken in a way users can hit right now; this is design debt that will keep costing every time an adapter is added. <!-- consolidation: discard; ref: none; reason: Historical prioritization superseded by the settled ruling. --> Do not pick (ii). <!-- consolidation: unconfirmed; ref: docs/BLUEPRINT.md#durable-conversation-and-operation-records; reason: Do not erase receipt recovery evidence without verified replacement. -->

## Decision 4 — Do zero-padded ids stay distinct, or become aliases?

**Situation.** `zeroPaddedIds` is a supported, documented feature, so `TASK-01` is a legitimate identity form. <!-- consolidation: integrate; ref: docs/specs/tasks.md#tasks-and-storage; reason: Settled distinct padded identity ruling requires supported identity-form coverage. --> But logical equality strips padding, so `task-1/` (TASK-1) and `task-01/` (TASK-01) are both valid container names while being logically equal. <!-- consolidation: discard; ref: none; reason: Old equality behavior superseded by settled distinct identities. --> Allocation now refuses to mint such a pair, yet legacy or hand-made records can still contain both — and the product then rejects with an ambiguity error rather than silently guessing which one you meant. <!-- consolidation: discard; ref: none; reason: Historical allocator behavior evidence. --> `src/test/local-task-command-performance.test.ts:276-305,334-380` builds exactly that collision and asserts the rejection: 2 failures. <!-- consolidation: discard; ref: none; reason: Historical failing test count. -->

A second suite depends on the same policy. `src/test/readiness-surface-agreement.test.ts` asserts a fail-closed result for an identity claimed by more than one record, but its fixture uses two records sharing one flat id — a shape canonical layout cannot represent — so it currently fails on an obsolete flat path. <!-- consolidation: discard; ref: none; reason: Historical obsolete fixture diagnosis. --> Rewriting it as a **padding** collision (`task-1/` versus `task-01/`) would make the scenario constructible, which is why its fix belongs with this decision rather than the fixture batch. <!-- consolidation: discard; ref: none; reason: Historical fixture rewrite recommendation not durable requirement. -->

**Why it matters.** It decides whether the product absorbs the padding distinction (treating a padded id as an alias of the unpadded one) or treats it as a genuine separate identity whose collision is an error. An alias rule is compatibility behavior that must live in the codebase permanently — the same category as the flat-record support already removed. <!-- consolidation: discard; ref: none; reason: Historical alternative framing resolved by distinct identities and no compatibility aliases. -->

**Options.**
- **(a) Keep them distinct and fail closed.** Collisions are reported, never guessed; the test asserts the rejection. Consistent with the standing policy. **Recommended.** <!-- consolidation: integrate; ref: docs/specs/tasks.md#tasks-and-storage; reason: Settled ruling needs explicit distinct-ID and ambiguity behavior. -->
- **(b) Normalize padded ids to unpadded.** Friendlier for legacy data, but it keeps compatibility behavior forever and reintroduces ambiguity unless padding is dropped as a feature entirely. <!-- consolidation: discard; ref: none; reason: Unchosen permanent alias alternative. -->

**Recommendation: (a).** If padded ids ever need to go away, that is a one-time manual conversion of the padded records, not a permanent alias rule. <!-- consolidation: exists; ref: docs/CONVENTIONS.md#changes-and-refactoring; reason: Removal requires explicit preservation policy rather than permanent compatibility. -->

## Decision 5 — Pre-existing bug: task creation from a linked git worktree fails

**Situation.** `saveTask` throws `Task <id> resolves outside active task storage` when a task is created from a linked worktree. Confirmed by A/B testing **HEAD itself** in a temporary worktree: both `src/test/worktree-task-id-allocation.test.ts` (0/4) and `src/test/worktree-refresh.test.ts` (1/1) fail at HEAD with the same error. This predates the current session's work entirely — it is not a regression. <!-- consolidation: discard; ref: none; reason: Historical worktree bug reproduction. -->

**Cause.** Two root notions disagree. `TaskArtifactRepository.root()` (`src/file-system/task-artifact-repository.ts:113–120`) deliberately maps a linked worktree's backlog path to the **main** worktree's store, so the container it returns lives under main. But `saveTask`'s guard compares that container's parent against the **active** root, which for a linked worktree is derived from that worktree's own resolved backlog directory (`src/file-system/operations.ts:197–204,363–365,733–736`). They can never match, so creation always throws. <!-- consolidation: discard; ref: none; reason: Historical root-resolution defect diagnosis. -->

**Why it matters.** Anyone running `backlog` from a git worktree cannot create tasks. <!-- consolidation: discard; ref: none; reason: Historical defect impact. --> The failing tests also imply a third expectation — that allocation should scan *sibling* worktrees for uncommitted tasks — which only makes sense if each worktree has its own store. <!-- consolidation: discard; ref: docs/specs/tasks.md#tasks-and-storage; reason: Sibling task discovery is superseded by one project store. -->

**Options.**
- **(a) Tasks live in the main worktree's store.** Make the active-root resolution use the same linked-worktree → main mapping as `root()`, so guard and container path agree. Small and coherent, but it contradicts what the sibling-scanning tests expect. <!-- consolidation: exists; ref: docs/specs/tasks.md#tasks-and-storage; reason: Chosen shared main-project store is explicit. -->
- **(b) Tasks live per worktree.** Drop the main-worktree remap from `root()` and let each worktree use its own `backlog/`, with the sibling scan doing cross-worktree allocation. Larger; changes storage semantics and how worktree tasks are found and committed. <!-- consolidation: discard; ref: docs/specs/tasks.md#tasks-and-storage; reason: Per-worktree task stores are rejected. -->
- **(c) Leave it for now.** Out of the original scope; record it as a known pre-existing bug. <!-- consolidation: discard; ref: none; reason: Old deferral superseded by settled shared-store ruling. -->

**Recommendation: (c) now, then (a) or (b) as its own piece of work.** It is a design question about where tasks live, not a compatibility issue, so it should not be folded into the legacy cleanup. If the sibling-scan tests encode the intended design, (b) is the better fit — but that needs confirming with whoever wrote them rather than my reading. <!-- consolidation: discard; ref: docs/specs/tasks.md#tasks-and-storage; reason: Earlier recommendation superseded by approved main-project store. -->
