## Finding

`PRD`, `SRS`, and `SPEC` are labels, not one universal document taxonomy. ISO/IEC/IEEE 29148 defines requirements-engineering processes and information items; NASA uses names such as Software Requirements Specification and System Requirements Document. Neither establishes that a file named `SPEC.md` must use one exact structure. <!-- consolidation: discard; ref: none; reason: External naming research is supporting context rather than a durable project contract. --> Treat the chosen filename as local convention; define authority and scope explicitly. <!-- consolidation: unconfirmed; ref: none; reason: Local SPEC authority and linked ownership are explicit. -->

## Source-supported principles

- A requirements baseline describes intended product behavior and constraints; implementation is verified against it, while validation asks whether it meets stakeholder purpose. NASA's handbook separates verification from validation and recommends requirements that are clear, feasible, necessary, traceable, and verifiable. <!-- consolidation: discard; ref: none; reason: External requirements-engineering guidance remains research evidence rather than a project-specific mandate. -->
- Requirements cover functions and performance as well as constraints/quality attributes. NASA guidance calls for operational scenarios, including off-nominal/degraded conditions. SEI describes system requirements as capabilities, behavior, information, conditions, qualities, and constraints, and emphasizes traceability to source, architecture, and tests. <!-- consolidation: discard; ref: none; reason: External scope and traceability guidance is supporting research not approval of new quality guarantees. -->
- The standard's public abstract confirms that 29148 specifies requirements-engineering processes, information items, their contents, and format guidance. Its current 2018 edition was confirmed in 2024; ISO says revision is expected. The full standard is paywalled; do not claim its detailed clauses from the abstract. <!-- consolidation: discard; ref: none; reason: Time-specific standards status and citation limitations stay with the research source. -->
- Diátaxis distinguishes reference (accurate technical facts) from how-to/action guidance and explanation. This supports keeping enduring product reference separate from work plans, but is a documentation-design analogy, not a requirements standard. <!-- consolidation: discard; ref: none; reason: External documentation analogy need not be imported into core. -->

## Recommendation (judgment, not a standards mandate)

Use one authoritative **product contract** (keep `docs/SPEC.md` unless there is a compelling local reason to rename it). <!-- consolidation: unconfirmed; ref: none; reason: SPEC and its linked features are the single product authority. --> Make it a positive, exhaustive-enough statement of supported externally observable behavior—not a list whose identity is “things we do not have.” Enumerate supported public CLI/API operations and their semantics; include functional behaviors, meaningful quality/security/error constraints, user-visible boundaries, and representative normal, edge, failure, and recovery scenarios. <!-- consolidation: exists; ref: docs/SPEC.md#feature-contracts; reason: Feature contracts and the interfaces API baseline provide positive behavior and off-nominal outcomes. --> Add measurable acceptance/verification criteria where a claim needs a test; <!-- consolidation: exists; ref: docs/SPEC.md#feature-contracts; reason: Acceptance criteria belong with feature contracts. --> link each requirement or coherent section to relevant source implementation and test evidence. <!-- consolidation: unconfirmed; ref: docs/CONVENTIONS.md#documentation-maintenance; reason: Universal per-claim source and test linkage is not established as an accepted maintenance requirement. --> Evidence links establish implementation/verification status, not product intent. <!-- consolidation: unconfirmed; ref: none; reason: Evidence cannot change approved intent. -->

Track desired changes separately in the existing issue/task/roadmap mechanism (or a single scoped `docs/` backlog only if no tracker exists): <!-- consolidation: discard; ref: none; reason: Owner explicitly selected the temporary file ledger until the application is usable regardless of tracker existence. --> removal/deprecation of an existing command, migration/compatibility steps, and implementation gaps belong there with owner, status, and completion criteria. Link backlog items to affected contract sections. <!-- consolidation: unconfirmed; ref: none; reason: Alignment ledger owns implementation actions and links their contracts. --> Do not put planned removal in the normative contract as though already true; update the contract when the agreed baseline changes. <!-- consolidation: unconfirmed; ref: none; reason: Approved intent is distinguished from implementation completion. --> Avoid a parallel PRD/SRS that repeats the same contract. <!-- consolidation: exists; ref: docs/SPEC.md#features; reason: One owning feature contract replaces abbreviated duplicates. -->

Negative requirements are legitimate when they constrain an unsafe or unwanted outcome: e.g. “uncertain liveness evidence does not authorize stopping an agent” or “deleting a running session is refused.” Preserve these as positive safety invariants (condition + prohibited outcome + observable response), not merely “feature X is absent.” <!-- consolidation: unconfirmed; ref: none; reason: Safety constraints remain approved and the session contract retains both named invariants. --> A non-existent command may be stated as a precise current API boundary when needed to make the supported API exhaustive, but avoid a growing catalog of absent/potential commands. <!-- consolidation: exists; ref: docs/specs/supported-integration-operations.md#supported-integration-operations; reason: Positive approved API baseline distinguishes unresolved entry points from rejected behavior. --> Distinguish deliberate policy from temporary omission and link a planned change to its backlog item. <!-- consolidation: unconfirmed; ref: none; reason: Contract approval and ledger work are distinct. -->
