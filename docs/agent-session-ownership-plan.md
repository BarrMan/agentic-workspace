## 1. The spec

| Context of the invocation | `agent-session start TASK-x` |
|---|---|
| A live workspace owns the calling context | The session record is created and **owned by that workspace** (`ownerPid` = the workspace pid, `nativeWorkspace: true`, `tmuxName` = the workspace's private socket). The CLI does **not** launch anything. The workspace adopts the record and launches it exactly as if Enter had been pressed — private socket, VT transport, native host — and it dies when the workspace exits. <!-- consolidation: discard; ref: docs/BLUEPRINT.md#launch-context-and-terminal-transport; reason: Private frontend backend and frontend-owned execution are superseded by shared runtime. --> |
| No live workspace | The CLI launches the agent on the shared `default` server (native conversation, log, brief), then **stops it immediately** as the command exits. The record is left `stopped`, resumable. The next workspace shows it stopped and offers resume (`workspace-controller.ts:1015`: "Agent stopped; select this session to resume its exact conversation"). <!-- consolidation: discard; ref: docs/specs/sessions.md#live-terminal-and-client-lifetime; reason: CLI-exit stop and historical stopped record are superseded by independent execution lifetime and observed state. --> |

Consequences that follow, and are intended:

1. **A CLI invocation never leaves an unowned running agent.** Either the workspace owns it or it is dead by the time the command returns. <!-- consolidation: discard; ref: docs/specs/sessions.md#live-terminal-and-client-lifetime; reason: Client exit no longer ends execution. -->
2. **The socket is not a launch target for the CLI.** It travels in the context only as a *liveness token* proving which workspace owns the invocation. All launching stays in the workspace process, which is what makes "exactly like the UI" true instead of approximated. <!-- consolidation: discard; ref: docs/BLUEPRINT.md#launch-context-and-terminal-transport; reason: Explicit shared backend replaces private socket ownership token and UI-only launch. -->
3. **Unowned-start is deliberate.** The owner chose "launch, then stop it immediately" over "record only", so the native conversation exists and `resume` continues it. <!-- consolidation: discard; ref: docs/specs/sessions.md#live-terminal-and-client-lifetime; reason: Historical immediate-stop decision is superseded. -->

## 3. The context channel

**Variable:** `AGENTIC_WORKSPACE_WORKSPACE_CONTEXT`. Value: compact JSON `{"v":1,"pid":<workspace pid>,"socket":"<ink-proto-<pid>-<n>>","rootDir":"<abs project root>"}`. <!-- consolidation: discard; ref: docs/specs/sessions.md#inputs-delivered-to-the-agent; reason: Historical private-workspace context wire shape is not the explicit trusted identity contract. -->

**Written** only at the workspace's own agent-pane launch site, into the `prepared.env` copy that becomes the pane command (`workspace-controller.ts:1079-1081`). Never written to the workspace's own `process.env`, never persisted into `presetSnapshot.env`, never inherited by anything the workspace did not launch as an agent pane. <!-- consolidation: discard; ref: docs/specs/sessions.md#inputs-delivered-to-the-agent; reason: Private context propagation is replaced by explicit trusted child environment without launcher inheritance. -->

**Read** by the CLI through one module, `src/agent-workspace/workspace-context.ts`: <!-- consolidation: discard; ref: none; reason: Historical implementation module placement. -->

- `readWorkspaceContext(): WorkspaceContext | undefined` — never throws; any failure returns `undefined` and the caller takes the unowned branch. <!-- consolidation: discard; ref: docs/specs/sessions.md#trigger-and-scope; reason: Superseded owned versus immediate-stop branch API. -->
- Validation, all required: parseable JSON with `v === 1`; `pid` a positive integer and not this process's pid; the pid is alive; `rootDir` realpath-equals this project's root; and the socket answers `tmux -L <socket> list-sessions`. The last check is the real proof — it distinguishes a live workspace from a stale env inherited by a surviving child of a dead one, and it is the **only** use of the socket here. <!-- consolidation: discard; ref: docs/BLUEPRINT.md#architectural-invariants; reason: Obsolete context validation cannot substitute for current exact provenance and shared socket access alone is insufficient authority. -->

### The request marker, and why a marker exists at all

The durable record alone is not enough to make adoption *timely*: the workspace's refresh is event-driven, so a record written by another process can sit unnoticed until the user presses a key. The channel therefore has a second, non-durable half: <!-- consolidation: discard; ref: none; reason: Historical request-marker design rationale tied to old refresh implementation. -->

- `workspaceRequestDir(rootDir)` = `<project root>/.agentic-workspace/agent-requests`; one JSON file per pending request (`{ taskId, sessionId, pid }`), written by `writeWorkspaceRequest` after the durable record exists, deleted by `deleteWorkspaceRequest` on adoption, on cancel, and by the boot sweep. <!-- consolidation: discard; ref: none; reason: Historical queue representation and helper placement are implementation inventory. -->
- The controller's request timer (started at boot, rescheduled at `min(activityInterval, 1 s)`) **readdirs only that directory** and reads only the requested task's state — never a global `readAll()` per tick. `readWorkspaceRequests` never creates the directory and never throws: an absent directory is the normal state. <!-- consolidation: discard; ref: none; reason: Old adoption timer mechanics are not new observation or queue requirements. -->
- A marker whose `pid` is not this process, or is not alive, never launches a session. <!-- consolidation: unconfirmed; ref: docs/BLUEPRINT.md#architectural-invariants; reason: Queue-specific foreign-owner rejection must remain until retained adoption paths and retirement are verified. -->
- If writing the marker fails, the durable record is removed again, so a task is never left reserved by a request nobody can see. <!-- consolidation: exists; ref: docs/specs/sessions.md#creation-failure-and-recovery; reason: Critical pre-execution failure requires durable provisional rollback with truthful incomplete-settlement evidence. -->

### Phase S3 — Workspace adoption
**Deliverable:** a pending record owned by this workspace is launched exactly once, and pending records nobody owns settle stopped. <!-- consolidation: exists; ref: docs/architecture/task.md#session-relationship-operations; reason: Registering existing membership must not allocate a second execution. --> <!-- consolidation: discard; ref: docs/specs/sessions.md#identity-and-observed-state; reason: Missing frontend owner alone cannot prove stopped runtime. -->
**Slices:** (a) `sessions.adoptPendingSession(taskId, socketName, sessionId)` — asserts `STARTING` + `nativeWorkspace` + `ownerPid === process.pid`, then runs the launch path in **adopt** mode: same body as `prepareNativeSession`'s post-record launch, but `resume: false` (the record was never launched, so `buildAgentResumeCommand` must not run). (b) Controller: on the existing refresh path, adopt records from the snapshot it already holds — `STARTING` + `nativeWorkspace` + `ownerPid === process.pid` + not currently hosted/launching — by calling the normal launch path with the record's id. **Stop condition:** no path launches a record twice, and no path adopts a record owned by another pid. <!-- consolidation: exists; ref: docs/architecture/session-harness.md#session-operations; reason: One creation does not allocate another execution or identity during publication. --> <!-- consolidation: unconfirmed; ref: docs/BLUEPRINT.md#architectural-invariants; reason: PID-specific adoption rejection needs scoped queue-path disposition while provenance safety remains mandatory. -->

## 5. Invariants this plan must not break

1. **Native records keep `ownerPid`.** Demotion depends on it (`sessions.ts:487`). Only shared-server CLI records clear it (`sessions.ts:307`). <!-- consolidation: discard; ref: docs/BLUEPRINT.md#decision-reconciliation; reason: Historical field and demotion rules are not permanent schema requirements. --> <!-- consolidation: exists; ref: docs/architecture/application-boundaries.md#durability-checkpoint-collaboration; reason: Durable ownership evidence remains necessary despite field redesign. -->
2. **No new durable field, no `SessionState.version` bump.** Pending-ness is derived: `STARTING` + `nativeWorkspace` + live owner pid + not hosted in this process. <!-- consolidation: discard; ref: docs/BLUEPRINT.md#decision-reconciliation; reason: Historical schema freeze and label-derived pending representation are superseded. -->
3. **The sidecar stays process-scoped and deterministic** (`sessionActivityDir`), and a hard-killed session must read as absent, never as a live status. <!-- consolidation: unconfirmed; ref: docs/architecture/session-harness.md#runningexecution-interaction-contract; reason: Exact sidecar scoping and stale-sidecar rejection require verification or explicit retirement in runtime work. -->
4. **One server per workspace; the CLI never kills a server.** `killWorkspaceServer` keeps refusing foreign socket names (`socket.ts:44-49`). <!-- consolidation: discard; ref: docs/BLUEPRINT.md#launch-context-and-terminal-transport; reason: Per-workspace server is superseded by shared backend. --> <!-- consolidation: exists; ref: docs/BLUEPRINT.md#architectural-invariants; reason: Client backend access cannot authorize foreign or shared-server termination. -->
5. **Adoption is not a second launch.** Exactly one host per record, guarded by the tracked/launching set. <!-- consolidation: exists; ref: docs/architecture/task.md#session-relationship-operations; reason: Registration reuses existing identity without allocating another execution. --> <!-- consolidation: unconfirmed; ref: docs/specs/sessions.md#creation-failure-and-recovery; reason: Tracked-set implementation gate remains until retained adoption path is reconciled. -->
6. **A record owned by another live pid is never adopted or resumed** (`sessions.ts:129-134` semantics stay, relaxed only for self). <!-- consolidation: unconfirmed; ref: docs/BLUEPRINT.md#architectural-invariants; reason: Historical PID guard cannot be retired without mapping exact execution ownership protection to the shared runtime. -->

## 6. Deliberately not doing

1. **`agent-session attach` on an owned session.** `attach` uses the shared `default` server (`session-process.ts:128-133`); an owned session lives on the workspace's private socket, so the CLI cannot attach to it. Gap, documented, not fixed here. <!-- consolidation: discard; ref: docs/BLUEPRINT.md#launch-context-and-terminal-transport; reason: Historical private-socket attachment gap is superseded by shared attachment contract. -->
2. **VT transport for adopted records.** VT must be armed before the command starts; adoption launches the pane itself, so adopted sessions *do* get VT — but only because the workspace performs the launch. External (`agent-session` on `default`) panes keep replay + `send-keys`. <!-- consolidation: discard; ref: none; reason: Historical transport implementation split is descriptive evidence. -->
3. **A global session scan per tick as the adoption trigger.** Dropped after measurement: the first cut relied on `#refresh`, which never runs on an idle workspace. The shipped trigger is a bounded readdir of the request-marker directory (§3) — one directory listing per tick instead of a full `readAll()` — so lifecycle Phase L1 stays free to narrow the refresh read to the active tab, and an IPC listener is unnecessary. <!-- consolidation: discard; ref: none; reason: Historical timer optimization and future lane scope are not new durable requirements. -->
4. **Unifying the two CLI transport paths, or giving the CLI its own server.** Out of scope by owner decision. <!-- consolidation: discard; ref: none; reason: Historical assignment scope does not constrain current shared-runtime alignment. -->

## 8. Residual limits

1. **A forged context can wedge one task.** An invocation that presents a live non-workspace pid, this project's root, and any live workspace-shaped socket registers a `starting` record nobody adopts and no sweep demotes (the owner pid is alive). Impact is limited to that task's session state, which `agent-session reset <task>` clears; it grants nothing, because the trust model is already "a local process that can write inside `.agentic-workspace`". <!-- consolidation: unconfirmed; ref: docs/BLUEPRINT.md#architectural-invariants; reason: Forged-context wedge and claimed reset remedy need current-path verification rather than acceptance as harmless. -->
