## Agreed decisions

### Agent identity and version selection

- Save the harness identity as `opencode`, not `opencode-v1` or `opencode-v2`. <!-- consolidation: integrate; ref: docs/BLUEPRINT.md#application-controller-and-stores; reason: Core separates provider from adapter identity but omits the agreed exact opencode persisted value. -->
- Select the version-specific adapter from the configured executable at execution time. Runtime adapter distinctions do not become saved session identities. <!-- consolidation: exists; ref: docs/BLUEPRINT.md#application-controller-and-stores; reason: Current resolved inputs and provider identity are separate from executable-version adapters. -->
- Treat existing historical OpenCode sessions as v2 sessions under the requested one-time manual migration. Do not leave them permanently classified as ambiguous or blocked. <!-- consolidation: unconfirmed; ref: docs/CONVENTIONS.md#changes-and-refactoring; reason: Historical v2 conversion applies only to a separately authorized migration whose compatibility remains unverified. -->
- Do not retain a legacy compatibility layer or historical unversioned-harness refusal guard. <!-- consolidation: unconfirmed; ref: none; reason: Legacy handling requires explicit exception. -->
- Preserve Backlog session IDs, native conversation IDs, and conversation history. Relabeling a record alone does not prove native resume compatibility; verify that separately. <!-- consolidation: exists; ref: docs/architecture/session-harness.md#session; reason: Application and provider identities remain distinct retained conversation evidence. --> <!-- consolidation: exists; ref: docs/architecture/session-harness.md#harness; reason: Saved provider identity alone does not prove exact resumability. -->

### Configuration

- Save the preset name, not a preset configuration snapshot. <!-- consolidation: exists; ref: docs/BLUEPRINT.md#application-controller-and-stores; reason: Persist preset identity rather than configuration snapshots. -->
- Resolve configuration normally when executing: task overrides, then project configuration, then user configuration. <!-- consolidation: exists; ref: docs/specs/configuration.md#configuration-and-modes; reason: Task project root precedence applies at execution. -->
- Task-specific configuration belongs on the task, not in a session's saved configuration scope. <!-- consolidation: exists; ref: docs/architecture/task.md#task; reason: Task owns overrides and current configuration access. -->
- Do not use saved commands, environment variables, preparation commands, or resume flags in preference to current resolved configuration. <!-- consolidation: exists; ref: docs/specs/configuration.md#configuration-and-modes; reason: Start resume and ask use current effective inputs. -->
- Configuration edits apply to existing sessions when they next execute. <!-- consolidation: exists; ref: docs/specs/configuration.md#configuration-and-modes; reason: Later execution uses updated effective configuration. -->

### Mode

- A session has one fixed mode; it does not move between modes. <!-- consolidation: exists; ref: docs/specs/configuration.md#configuration-and-modes; reason: Sessions retain their fixed owning mode. -->
- Save its mode identity, not both current mode and original creation mode. <!-- consolidation: exists; ref: docs/BLUEPRINT.md#application-controller-and-stores; reason: Persist fixed mode identity rather than snapshots. -->
- Do not save copies of mode prompts, permissions, or model selection in session creation snapshots. Resolve the current mode configuration for execution. <!-- consolidation: exists; ref: docs/BLUEPRINT.md#application-controller-and-stores; reason: Current resolved inputs replace saved configuration snapshots. -->
- Do not duplicate launch paths in a creation snapshot. Correct project/worktree targeting remains required; its minimal storage contract is still open. <!-- consolidation: exists; ref: docs/architecture/session-harness.md#harness; reason: Current validated paths are launch inputs rather than a saved configuration snapshot. --> <!-- consolidation: exists; ref: docs/BLUEPRINT.md#open-design-decisions; reason: Exact replacement recovery storage remains implementation work. -->

### Conversation versus runtime state

- The Backlog session ID to native harness conversation ID mapping identifies the conversation to resume. <!-- consolidation: exists; ref: docs/architecture/session-harness.md#session; reason: Distinct application and provider identities identify exact resume. -->
- Live-process bookkeeping is a separate concern from durable conversation identity. <!-- consolidation: exists; ref: docs/BLUEPRINT.md#durable-conversation-and-operation-records; reason: Runtime observation and unfinished-operation evidence are distinct from retained identity. -->
- Existing runtime fields are not accepted as permanently necessary merely because current code consumes them. Decide their replacement before deleting safety checks. <!-- consolidation: exists; ref: docs/architecture/application-boundaries.md#authoritative-mutation-and-publication; reason: Historical fields are not mandated but their safety and recovery purpose must survive. -->
